# Execution plan: Build and freeze a paired synthetic dataset

**Start here:** [Issue #4](https://github.com/akbarsahata/feedback-lab/issues/4) defines scope and closure criteria. Reuse the assignment snapshots and runner delivered by #1–#3. [#7](https://github.com/akbarsahata/feedback-lab/issues/7) will consume the frozen evidence; [#12](https://github.com/akbarsahata/feedback-lab/issues/12) will use the development split for the pilot and freeze the study protocol before authorizing held-out release. Use the [glossary](../../GLOSSARY.md) for domain terms.

## 1. Define the corpus package and validation rules

- Use a versioned `manifest.json`, individual UTF-8 `.py` files, a separate `scoring-key.json`, and a separate `verification.json`. The manifest gives the corpus a stable ID and revision and declares assignment family IDs, assignment definitions and revisions, split membership, stable case and submission IDs, and single or original/corrected membership. Use neutral source names that do not describe the expected bug or identify the corrected version.
- Reuse assignment validation in [`src/config.ts`](../../src/config.ts) and the existing source byte limit and hashing in [`src/upload.ts`](../../src/upload.ts). Keep function arguments and expectations in their lossless JSON-text fields; preserve script stdin/stdout and Python source bytes exactly. Validate referenced files and identifiers, reject missing or duplicate references, bound the upload and file count, and report issues by case or by package field before writing data.
- Assign each case, including both versions of a pair, to one split and one assignment family. Require each pair to use the same exact assignment revision. Reject contradictory split assignments and any family appearing in both splits. Document how authors group renamed copies, revisions, and close variants; researchers verify this grouping because a manifest validator cannot infer whether two exercises are variants.
- Give each expected error a stable ID and acceptable evidence references scoped to the submission and its pinned assignment, such as a rubric criterion, source range, or supplied study-test ID. Use an explicit clean designation. Record the targeted error on a pair in the scoring key: it must appear in the original and be absent from the corrected key; any unrelated remaining error keeps its identity. Keep targeted authoring checks and their results in the verification file, never in the supplied study suite.

**Checkpoint:** Valid single and paired cases in both formats parse with exact source and test values. Invalid packages report actionable case-level errors without creating assignments, submissions, or runs.

## 2. Persist drafts, verification, and immutable versions

- Add a D1 migration after `0003` for dataset revisions, case and submission membership, scoring-key revisions, researcher sign-offs, and held-out release records. Link to existing assignment, submission, and run records instead of copying their evidence into dataset tables. Keep stable package IDs separate from environment-local D1 IDs.
- Map imported assignment definitions to exact snapshots through [`src/repository.ts`](../../src/repository.ts). Track the revision and content digest of the import so retrying the same bytes resumes the same draft. Reject changed contents under the same package revision. Use uniqueness constraints and guarded writes to prevent duplicate membership or partially imported drafts from becoming visible to study callers.
- Add a small researcher-only dataset page with file upload, draft progress and per-case errors, verification, and freeze actions. Reuse [`requireResearcher`](../../src/guard.ts) and the existing authenticated POST/CSRF checks. Show the source, pinned requirements, scoring key, verification evidence, and study run status together for review. Record sign-off from the current authenticated researcher and server timestamp, tied to the exact case contents, assignment revision, submission source fingerprints, key revision, and authoring evidence. Uploaded verification notes alone do not count as sign-off.
- Freeze with a guarded D1 transaction: check current sign-offs, coverage, and complete recorded study evidence, then publish immutable membership and exact key/run references together. Reject stale or concurrent writes that would change the checked inputs. A correction produces a new frozen revision; earlier revisions and the evidence that their study runs reference remain readable.

**Checkpoint:** A migration test preserves existing assignment and run history. Repeat imports are safe, stale sign-offs cannot freeze changed cases, and a later dataset or assignment revision does not alter a previous freeze.

## 3. Collect study evidence through the current runner

- In [`src/runs.ts`](../../src/runs.ts), share submission/run creation with a dataset launch that takes an exact assignment version and checks that it belongs to the given assignment. Preserve the existing active-version guard on normal assignment uploads. Commit the draft's run reference with the submission, run, and pending test rows before calling [`dispatchRun`](../../src/dispatch.ts). Reuse the queue, coordinator, private runner, and reconciliation; do not add a parallel execution path.
- Make progress visible per submission and treat the D1-to-queue boundary as recoverable. Queued/running attempts cannot freeze. If an attempt becomes incomplete, give the researcher an explicit retry under the same exact assignment and source. Preserve the current one-run-per-submission constraint by creating a new submission/run record pair for that authored version, retaining the failed attempt. Guard the retry against concurrent requests; freeze pins the successful pair of records.
- Require a complete run with a recorded execution outcome for each test in the pinned suite. Use the existing execution status classification: a mismatch or submission-caused execution failure is evidence; `infrastructure_failure` and `not_run` block freeze. Check the all-tests-pass coverage requirement against actual recorded results and the independently verified key.

**Checkpoint:** Function and script drafts produce results using the pinned revision even after another revision becomes active. Simulate a dispatch or runner failure, verify freeze is blocked, then retry and freeze without losing the failed attempt.

## 4. Expose the study read path and enforce release

- Give #7 server-side list and direct lookup operations scoped to an exact frozen dataset revision and study use. Apply the same access rule before returning either result: the pilot can only read development cases; the main comparison can only read held-out cases after that dataset revision is released. Scope evidence lookup to a submission in the eligible case; a raw case, submission, or run ID grants no access on its own.
- Keep release separate from freeze. Store an explicit researcher release record for the frozen revision, with the actor, timestamp, and reference to the locked #12 protocol. Record release only after #12 authorizes it; a new revision starts unreleased. Authoring can inspect unreleased cases through the researcher-only authoring path.
- Build an allowlisted evidence projection for **one submission**: exact source, assignment instructions and format details, rubric, and supplied study tests and recorded results. #7 supplies this same frozen projection to both workflows; faithfulness evaluation uses it as well. Keep original/corrected labels, pair links, counterpart source, scoring-key data, and authoring evidence out of the projection. Expose pair links and the frozen key through a separate scoring read for known-error and correction outcomes.

**Checkpoint:** Exercise list and direct lookup for both splits before and after release. Confirm pilot access still excludes held-out cases after release, and compare the actual model-facing object to the allowlist, including tests with distinctive values in every excluded field.

## 5. Author, verify, and freeze the initial corpus

- Author four distinct introductory assignment families: one function and one script family per split. For example, use a range-counting function and an input total script for development, and a first-matching-item function and a per-line classification script for held-out. Check the final choices for shared templates or renamed variants across splits.
- For each family, author a clean single, a pair whose targeted fix leaves clean code, and a pair with a separately identifiable unrelated bug remaining. In each family, include a buggy submission that passes every supplied study test. Document the requirement and source range exposing that error, and verify it with a targeted authoring check where practical. The coverage matrix totals **12 cases and 20 submission versions**; this is inventory, not the sample size #12 will choose.
- Keep the held-out package and answer/verification files in restricted researcher storage. This repository is public: commit the package format, reproducibility instructions, and disposable example fixtures, while delivering the actual restricted files as versioned artifacts to the researchers. Record package digests and frozen revision IDs so the imported corpus can be identified without publishing its contents.
- In a fresh authorized environment with a working queue and the real private runner, import the package, review and sign off on each case, collect the supplied study-test results, and freeze the initial revision. Record the runner identity and frozen revision, show that both splits are present for authoring, and leave held-out unreleased. A fresh import should reproduce the logical corpus and key; local database IDs, timestamps, and run timings can differ.

**Checkpoint:** A researcher can follow the documented steps from an empty database to a complete frozen revision, verify the four coverage cells against actual run outcomes, and list only development cases through the pilot path.

## Verification before closing #4

- Run `npm run typecheck`, `npm test`, and `python3 -m unittest discover -s runner -p 'test_*.py'`.
- Use Workers integration tests for malformed files, auth and CSRF, split validation, import and retry concurrency, exact-version reads, sign-off invalidation, freeze atomicity, release and direct lookup, and the model input boundary. Use disposable fixtures for these tests.
- Record the fresh-environment import and real-runner freeze result in the implementation session. A fake-runner result checks application behavior but does not establish that the initial corpus was run and frozen. The hosted pilot belongs to #12.
